**Question 1 (GPU Coalescing vs. CPU Cache-Line Granularity):**
The column `u[1:257, 1]` has a row stride of 258 × 8 = **2,064 bytes**, so consecutive elements are 2,064 B apart and no two share a line or sector. A 64-byte CPU cache line therefore brings in 64 B to use 8 B per element: 256 elements → 256 lines = **16,384 B moved for 2,048 B useful** (12.5 % efficiency, 8× overhead); the hardware stride prefetcher can hide latency but not the wasted bytes. On the T4, a warp reading the column issues 32 separate 32-byte L2 sectors per request (fully uncoalesced): 256 elements → 256 sectors = **8,192 B moved for 2,048 B useful** (25 % efficiency, 4× overhead). `pack_halos_kernel` pays this strided cost once, on-device (GDDR6, ~320 GB/s), and writes the column into a contiguous 1D buffer, so the PCIe transfer carries exactly **2,048 B per column** (8,192 B for all four strips) as one dense DMA. Without packing, the strided data would cost about 8,192 − 2,048 = **6,144 B of wasted traffic per column (75 %)** over the far slower PCIe link (~12 GB/s). **Question 2 (Shared-Memory Tile Synchronization & PTX Audit):**
From `tiled_stencil_kernel.inspect_asm()` my counts are: `st.shared.f64` = ⟦n⟧, `ld.shared.f64` = ⟦n⟧, `bar.sync` = ⟦n⟧ (the kernel has one `cuda.syncthreads()` between the tile fill and the stencil). A 16 × 16 block has 256 threads = **8 warps**, each warp covering two rows of the tile (ty = 2w, 2w+1). Each thread stores its own cell `tile[ty+1][tx+1]`, and edge threads additionally store the ghost row/column of the 18 × 18 tile. In the stencil, a thread reads `tile[ty][·]` and `tile[ty+2][·]`, and for the first/last row of a warp those cells were written by a *different* warp (and the top/bottom halo rows by warps 0 and 7, the left/right halo columns by every warp). Without `cuda.syncthreads()` there is no ordering between warps, so a warp can issue its `ld.shared` **before** the neighbouring warp's `st.shared` has executed: a Read-After-Write hazard that returns stale/uninitialised shared data (from a previous block or garbage), giving wrong stencil values that vary from run to run. `bar.sync` forces all 8 warps to finish their stores before any warp loads.

**Question 4 (MPI-3 Shared-Memory MESI RFO Ping-Pong):**
Measured (best of 3, max over ranks, 40,000,000 updates each): stride 1 (8 B) = ⟦t1⟧ ms, stride 8 (64 B) = ⟦t8⟧ ms, stride 16 (128 B) = ⟦t16⟧ ms. False-sharing slowdown = t1 / t8 = ⟦ratio⟧×, i.e. ⟦t1 / 40e6 ⟧ ns vs ⟦t8 / 40e6⟧ ns per update. MESI trace for `shm_view[0]` (Rank 0) and `shm_view[1]` (Rank 1), same 64-byte line:
1. Initially the line is **I** (or **E/S**) in both cores.
2. Rank 0 writes: Read-For-Ownership; line goes **I → M** in core 0, any other copy → **I**.
3. Rank 1 writes a *different* word of the same line: its copy is **I**, so it issues an RFO; core 0 must supply the dirty line (write-back/forward) and goes **M → I**; core 1 goes **I → M**.
4. Rank 0 writes again: its copy is **I** → RFO; core 1 **M → I**, core 0 **I → M**.
This repeats on every update: one cross-core line transfer per write, tens of ns each, even though the ranks never touch the same bytes. With stride 8 each rank owns a private line that stays in **M** (after the first **E → M**, which is a silent upgrade), so no snoop traffic occurs.

**Question 5 (128-Byte Spatial Prefetcher Pairing & Padding Trade-Offs):**
Measured: stride 8 (64 B) = ⟦t8⟧ ms, stride 16 (128 B) = ⟦t16⟧ ms, ratio t16 / t8 = ⟦ratio⟧. Intel's L2 *adjacent cache-line (spatial) prefetcher* treats memory as 128-byte aligned pairs of 64-byte lines (an even and an odd line) and, on a miss to one, fetches the "buddy" line too. With stride 8, ranks 0 and 1 land in the two halves of the *same* 128-byte pair (bytes 0–63 and 64–127), as do ranks 2 and 3, so a prefetch of the buddy line can pull in a line another core is modifying and trigger extra coherence traffic. Stride 16 puts every rank in its own 128-byte pair, which removes that residual interference. ⟦Interpret your ratio: ≈1.0 means the effect is negligible/within noise on your CPU or a virtualised Colab host; < 1 means the prefetcher pairing was visible.⟧ The cost of too much padding is capacity: each 8-byte counter occupies 128 B (6.25 % utilisation vs 12.5 % at 64 B), so a working set holds half as many useful values in L1/L2, and a 128 B stride maps onto only every second cache set, which shrinks the effective associativity/sets and causes more capacity and conflict misses (plus more TLB pressure) when many counters are padded. With only 4 counters (512 B) this is negligible; it matters for large arrays of padded per-thread data.
